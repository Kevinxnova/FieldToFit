## 后续更新流程

1. 完成一项改动后把用户可感知的变化写入 CHANGELOG 的 Unreleased，标注完整新 REQ 和子项；更新对应实际状态与证据。文档修订单独标明，不以页面设计充作功能交付。
2. 准备实际软件版本时，参照 [说明模板](template.md) 创建版本文件，同步后端 `__version__`、frontend package 和 lockfile。
3. 检查 README 的“最近更新”、ROADMAP 和版本说明内容一致；更新真实截图，不把计划或模拟结果当作实测。
4. 运行必要检查，保留版本、输入和环境对应的证据；记录未完成事项与升级影响。
5. 确认发布后，为检查通过的同一提交创建标签和 GitHub Release；Release 正文来自该版本说明。开发候选不等于已经发布。

补丁版本用于修复；兼容新增功能用次版本；破坏兼容的改动需升级说明和主版本评估。原 API 路径与 MCP 协议版本单独管理。

## 内容更新与软件发版

每日内容变化使用对象修订、材料版本和概览期次，不每天提高软件版本。软件发版说明本版解决什么、变化重点、REQ/子项结果、证据、迁移和未完成项；README 最近更新只摘要并链接对应记录。历史版本的旧 REQ 名称和验证结果保留，现行优先级以 P1 清单与路线图为准。公开 Release/部署发生后才标已发布，不能把本地文档或开发候选当正式版。
