# FieldToFit 版本号规则

2026-09-11 用户确认。本规则优先于旧版“软件与内容分开、不必递增版本”的约定。当前起点为 **v1.0.1**。

| 位数 | 适用范围 | 决策和递增 |
| --- | --- | --- |
| z：补丁 | 修复、文案、资料、页面、配置、文档等日常修改 | 每次包含实际改动的交付提交都递增一次，并记录；无需再次询问。1.0.1 → 1.0.2。 |
| y：中等更新 | 新的完整功能模块、明显改变主要阅读或取材流程，但保持产品主线 | 助手主动判断，提交改动范围、用户影响和建议版本，与用户对齐并确认后递增；z 归零，如 1.0.8 → 1.1.0。 |
| x：大更新 | 产品方向重大改变、核心架构或兼容协议出现重大升级 | 助手说明升级原因、影响与迁移方案，与用户对齐并确认后递增；y/z 归零，如 1.4.6 → 2.0.0。 |

## 一次提交如何执行

1. 工作中的多次保存组成一批待提交改动，不按每次按键递增；每个包含实际改动的 Git 提交对应一个新版本。只有检查、没有修改则不递增。
2. 本次按用户明确要求使用 v1.0.1，内容和界面改动整合为一次交付提交。后续若另补文档、修复或数据并提交，也必须继续递增 z，不继续挂在旧版本。
3. 提交前同步 backend/__init__.py、frontend/package.json 和 package-lock.json。网页从实际版本读取，不再手写关于页版本号。
4. 同步 CHANGELOG、中英文 README 最近更新、docs/releases/vX.Y.Z.md、版本导航、REQ 和 ROADMAP。每项记录是什么、为何改变、验证结果与未完成边界。
5. 运行仓库版本一致性检查。提交说明使用 `release: vX.Y.Z ...`；避免同一交付再产生不递增版本的“补验收文档”提交。部署状态可以写在提交前，失败就如实记录。
6. 发布版本标签使用 `fieldtofit-vX.Y.Z`。旧 Metis 的 `v1.0.0` 不移动、不覆盖；标签/Release 仅在确实创建后标记可下载。

每日检查没有内容变动时只写运行记录，不生成空提交或新版本。审核后的新内容一旦修改仓库并提交，也递增 z；资料自身的修订号和核验日期继续保留，用于追溯具体内容，不能代替应用版本。运行数据库日志不属于源代码交付提交。

## 升级申请内容

提出 y 或 x 升级时同时给出：当前和建议版本、本轮范围、为什么超过日常更新、用户可感知变化、兼容/迁移影响、验收和回滚方案。未收到确认前维持已授权的补丁更新范围，不擅自提升 y/x。
