## 1. 项目目标

### 1.1 产品定位

**FieldToFit 面向研究者、工程师、研究生和学生，持续维护 AI 领域的动态、研究资料与可用资源，让人理解变化，让 AI 在学习、研究、设计、选型和二次开发时获得可靠依据。**

平台包含信息、应用两个模块。每个模块分别面向人和 AI 提供不同的交付方式，使用同一套可追溯的事实数据。

### 1.2 核心问题

**AI 领域的动态、研究成果和工具资料分散、持续变化，用户及其 AI 助手难以把这些信息转化为可追溯、可执行、可验证的学习、研究与开发行动。**

用户在具体任务中需要知道：已有研究解决了什么、还存在哪些限制，哪些模型、数据、代码或工具符合自己的条件，以及应该学习、复现、直接使用、基于开源修改，还是自行实现。

人类阅读场景还需要解决：重点是什么、变化意味着什么、哪些内容值得继续了解。

### 1.3 目标及可观察结果

| 编号 | 目标 | 可观察结果 |
| --- | --- | --- |
| G-01 | 持续掌握 AI 领域的重要变化 | 用户能查到覆盖范围内的事件、来源、发生时间和具体变化，并知道数据是否过期。 |
| G-02 | 帮助人理解和发现 | 用户从摘要、案例和对比中理解一个事件或工具，并能进一步查看依据。 |
| G-03 | 帮助 AI 做研究和开发决策 | AI 能按任务条件找到研究资料及候选方案，说明符合项、不符合项、未知项和采用路径，并提供依据。 |
| G-04 | 帮助 AI 支持学习、复现和工程实践 | AI 能拿到原文定位、前置知识、与版本对应的文档、运行条件、示例和验证方法，支持学习、实验复现、集成及二次开发。 |
| G-05 | 形成持续使用和自然传播 | 用户因为解决了具体问题而复用、分享或自行部署 FieldToFit，并反馈实际用途。 |

G-03、G-04 解决信息获取和使用依据的问题。FieldToFit 提供的资料仍需由用户及其 AI 助手结合任务验证；资料检索完整性、研究新颖性和完整实验复现不能仅由生成模型自行宣布成立。

本轮暂不把 token 消耗、模型响应速度作为首要优化目标。首先验证资料正确性、需求匹配和实际任务结果。

## 2. 已对齐事项与待验证假设

### 已对齐

- 持续收集 AI 圈动态，覆盖模型、Agent、生态、商业、垂直领域等主题，以及值得关注的工具。
- 分为信息、应用两个模块，每个模块提供人类视图和 AI 使用方式。
- 人类内容重视筛选、层次和解释；AI 内容重视可查询的事实、条件、版本、关系与详细依据。
- 共享事实数据，根据使用对象形成不同的表达和查询结果。
- AI 使用场景涵盖自主设计、直接采用现有工具、基于开源项目开发；同一项目可以混合采用三条路径。
- 目标用户确定为研究者、工程师、研究生和学生；身份可以重叠，按实际任务组织内容。
- 人类页面、AI 查询、MCP、自部署以及本稿其余需求均纳入本轮交付；实现按依赖顺序推进。
- 首批来源、覆盖范围和资料整理深度由本稿提出具体方案。
- 当前版本暂不开放账户注册、登录与账户同步。“我的账户”和“账户与同步”入口置灰、不可点击，并标注“待开放”；直接访问账户页展示说明，不展示登录或注册表单。浏览、检索及本地收藏和关注无需账户，继续可用。账户开放时间另行确定。

### 已知用户信号

作者通过自媒体发布 FieldToFit 后获得关注；有人询问 MCP，有人自行部署开源项目。

这些反馈说明存在接入和部署兴趣。其具体用途、持续使用程度以及任务收益尚未核实，不能直接当作已经验证的产品需求。

### 本稿提出的假设

- 按四类用户各三个任务构成首批 12 个验收场景，同时覆盖学习、文献理解、实验复现、工具选型与二次开发。
- 数量、调度频率和资料完备度目标是方案建议，不是已测得的服务能力。
- “应用”覆盖可用于任务的成品应用、API 服务、模型、Agent、框架、库、数据集、评测基准和可复用开源项目。论文主要作为研究资料进入信息模块，与相关应用资源建立关系。

### 用户与主要任务

| 用户 | 主要任务 | 平台交付 |
| --- | --- | --- |
| 研究者 | 跟踪方向、比较方法及实验依据、寻找相关模型与数据 | 带原文定位的研究资料、方法与基准对比、论文与实现的关联、方向更新。 |
| 工程师 | 方案设计、选型、集成、二次开发、跟踪依赖变化 | 按条件筛选的资源档案、开发资料、版本与限制、可运行案例。 |
| 研究生 | 阅读论文、组会准备、寻找基线、复现实验 | 论文方法与局限、代码及数据入口、复现步骤、引用信息、实验条件。 |
| 学生 | 理解概念、寻找学习材料、完成实践项目 | 分层解释、前置知识、官方教程、难度和硬件要求、最小实践。 |

四类用户共享信息与应用页面，通过主题、任务和阅读深度获得不同结果，不建设四套独立内容库。

## 3. 产品结构与基本概念

### 3.1 四种交付

| 模块 | 面向人 | 面向 AI |
| --- | --- | --- |
| 信息 | 动态流、主题浏览、双语简报、研究解读、事件及论文详情 | 事件与研究资料查询、原文定位、变化记录、方法与实验条件、来源及关联实体 |
| 应用 | 模型、工具和研究资源档案、任务案例、门槛、优缺点、候选对比 | 能力与限制、输入输出、版本、依赖、运行条件、模型和数据说明、文档、示例及验证状态 |

“给 AI 看”不限于 JSON，也包括带元数据的 Markdown、详细文档和按需读取的原始材料。两种表达对相同事实必须保持一致。

### 3.2 数据对象

| 对象 | 含义 | 示例 |
| --- | --- | --- |
| 来源材料 | 来自外部的原始记录或可访问引用 | 公告、论文、模型卡、数据卡、仓库说明、更新记录、讨论、RSS 文章 |
| 研究资料 | 具有稳定引用身份的研究对象 | 论文及其不同版本、方法、作者报告的实验、公开评审与出版状态 |
| 事件 | 在特定时间发生的事情或变化 | 发布模型、调整价格、增加能力、融资、停止维护 |
| 应用档案 | 可持续查询和更新的工具或能力实体 | 一个模型、一项 API 服务、一个开源项目 |
| 证据记录 | 支持某一项具体判断的材料及其适用范围 | 某版本文档支持的能力、某环境下的测试结果 |
| 关联关系 | 事件、应用和相关组织之间的联系 | 发布、依赖、集成、替代、影响 |

主题和对象类型分开：一个 Agent 项目可以属于编程、办公等多个主题；“Agent”不必和“垂直领域”互斥。

一个模型发布事件进入信息模块，模型的能力档案进入应用模块，通过关系连接。事件历史与应用当前状态分别保留。

### 3.3 贯穿案例

某项目发布了支持本地中文 PDF 处理的新版本：

1. 采集公告和相关文档，保留来源与时间。
2. 将多处报道合并为一个事件，保留各自材料。
3. 关联到已有应用档案，新增该版本的能力记录与限制。
4. 人类用户看到变化摘要、适用场景和原文入口。
5. AI 查询“支持本地部署的中文 PDF 处理方案”时，获得匹配结果、版本和依据。
6. AI 按需获取运行说明及示例；未知条件明确列出，测试结果标明适用环境。

## 4. 本轮交付范围

2026-09-06 补充确认：所有来源的检查和更新周期统一为 1 天；当前前端彻底重构，重新设计导航、页面结构、查询、详情、对比和移动端体验。

作者要求全部推进。本稿所有需求均标为“本轮”，包含已有 36 项及面向研究、学习所补充的需求；MCP 与网页、AI 查询一起验收。

工作按依赖组织：共享数据与采集 → 查询及资料组织 → 人类页面和 MCP → 场景验证与部署。该顺序用于实现协调，不代表将后面的模块推迟到另一代产品。

功能范围完整交付，资料覆盖范围按第 7 节的来源与样本方案建设。每条记录的“基础档案、完整资料、已验证”表示内容状态，不表示功能分期。

## 6. 功能交付与内容覆盖的边界

**以上 42 项保留为完整产品需求。** 网页、AI 接口、MCP、研究学习支持、本地收藏关注、导出、模型配置、人工及自动验证继续推进。按 2026-09-07 的最新决定，账户注册、登录、跨设备同步及依赖账户的个性化订阅暂不作为当前开放版本的验收项。验收既检查功能，也检查第 8 节的真实任务产物。

资料库持续扩充。某项资源可以已被发现但尚未读到完整文档，也可以资料完整但没有运行实测；两端均显示这些状态。自动验证功能覆盖选定且具备运行条件的案例，完整论文实验复现另行记录其实际完成范围。

本轮不额外引入全网秒级抓取、所有历史资料、任意项目自动开发部署、完整社交社区、交易市场、计费或复杂团队协作。这些不属于当前提出的 42 项需求。热度可以帮助发现内容，不能替代任务适配、研究质量或实验依据。

## 7. 首批来源、资料深度与更新方案

本节是建议采用的具体方案。数量和时效是建设及验收目标，尚未经过采集或运行验证；来源接入时记录实际可用入口、权限、更新机制和失败情况。

### 7.1 六类来源

| 来源类别 | 首批范围 | 采集内容与用途 | 建议更新方式 |
| --- | --- | --- | --- |
| 论文与研究 | arXiv 的 cs.AI、cs.LG、cs.CL、cs.CV、cs.RO、stat.ML；OpenReview 上目标会议的公开记录；官方会议论文页面 | 论文元数据、版本、可访问正文、公开评审状态、作者给出的代码和数据链接。arXiv 与会议记录通过论文身份关联。 | arXiv 按日增量；会议公开资料每日检查，按实际发布节奏调整。 |
| 官方模型、Agent 与生态动态 | 先维护 10–15 个机构或团队的官方入口，例如 OpenAI、Anthropic、Google DeepMind、Meta、Microsoft、Qwen、DeepSeek、Kimi、GLM、MiniMax | 官方博客、公告、文档变更、模型卡与仓库发布；覆盖国内外团队，同步识别停用、费用和接口变化。 | 公告订阅或每 1 天检查；在每日任务内更新相关档案。 |
| 模型、数据及演示资源 | Hugging Face 的 Models、Datasets、Spaces，以及相关作者官方仓库 | 发现模型、数据和应用，读取模型卡、数据卡、许可证、依赖和关联论文；演示与可复用代码分别标注。 | 关注对象每 1 天检查可用更新；变更线索在每日任务中统一处理；发现列表每日更新。 |
| 开源工程项目 | 现有 GitHub Trending，加人工种子、任务检索和已关注仓库 | Trending 发现项目；仓库说明、Release、文档及示例提供能力依据。议题用于发现具体故障线索，区分报告与已确认问题。 | 关注仓库的发布每 1 天检查；元数据每日更新；每日任务发现版本变化后重新读取。 |
| 商业与垂直领域信息 | 现有可用 RSS，补充产品官网及公司公告，按医疗、教育、办公、编程等主题归类 | 行业变化、融资、产品推出、业务采用案例；媒体报道保留原始归属，可核实事项关联一手来源。 | RSS 每 1 天；无订阅入口的官方页面按来源配置。 |
| 社区关注与新产品 | 现有 Hacker News、Product Hunt，加用户提交的公开链接 | 发现讨论和新工具，记录来源内的热度及变化；回到论文、官网或仓库整理事实。 | HN 和 Product Hunt 每 1 天；遵循实际接口限制。 |

来源优先级：官方及作者材料支撑事实，媒体补充背景，社区提供发现线索。不同来源的热度分别记录，不直接把 Star、点赞、下载和论文引用混为一个质量分数。历史快照足够后再呈现增长趋势，不能用单次读数虚构增长。

公开社交帖和视频链接可通过用户提交进入发现流程；暂不依赖对所有社交平台的全文抓取来完成上述功能。来源失败时保留历史数据并显示过期状态。

上述接入方向的依据：arXiv 官方 API 提供分类检索及版本时间，其更新说明支持按日增量的设计；Hugging Face 官方 API 覆盖模型、数据集和 Spaces，并提供变更通知相关入口；GitHub 官方接口提供发布记录。具体采集周期是 FieldToFit 的设计建议。[arXiv API 手册](https://info.arxiv.org/help/api/user-manual.html)、[Hugging Face Hub API](https://huggingface.co/docs/hub/api)、[GitHub Releases API](https://docs.github.com/en/rest/releases/releases)。

OpenReview 作为拟接入来源，先验证目标会议公开记录的可用性；无法通过接口读取时保留可访问的官方会议入口及状态，不把接入名单等同于已采集成功。

### 7.2 初始资料规模

建议以 **200 个去重后的资源档案、100 篇研究资料、60 份完整任务资料包、12 个验证案例** 作为起始建设目标，随后持续采集和补全。

- 200 个资源的主类型分配：50 个模型、30 个 Agent 或框架、40 个开发工具或库、30 个数据集或基准、30 个垂直应用、20 个学习或复现项目。每个对象只计一次，可以有多个主题标签。
- 100 篇研究资料兼顾近期论文与验收任务所需的基础研究；数量不足时不以低相关内容补齐。
- 60 份完整任务资料包围绕第 8 节的场景组织，可引用多个资源或论文，也可被多个任务复用。其完整性由资料字段及依据决定，不等于已经实测成功。
- 12 个验证案例对应四类用户各三个任务。建议其中八个包含可控环境下的代码或数据运行，四个验证阅读、比较和引用产物；条件不允许时记录实际覆盖，不能改名为已完成复现。

动态优先补采可获得的最近 90 天记录；论文先获取最近 30 天候选并按任务补入基础文献。受接口历史范围限制的缺口须显示。成熟工具不因发布时间较早而被排除，当前能力档案与近期动态分别维护。

### 7.3 三种资料状态

| 状态 | 包含内容 | 覆盖策略 | 可以对用户作出的表述 |
| --- | --- | --- | --- |
| 基础档案 | 身份、来源、时间、类型、任务标签、可获取的原文材料、字段缺失及读取范围 | 所有正式入库对象；未处理对象进入待整理队列 | 已发现并整理了这些来源；具体能力按证据标注，不宣称已全面核验。 |
| 完整资料 | 基础档案，加任务相关的方法或能力、限制、条件、关联资源、版本对应文档、操作或复现说明及定位依据 | 首批重点对象；用户关注、查询缺口和重要变化触发补全 | 在声明范围内具备任务所需资料；缺少关键原文或条件时保持部分完成状态。 |
| 验证记录 | 关联完整资料，记录核验方法、输入、版本、环境、执行步骤、结果、失败或未覆盖条件 | 12 个初始案例及后续可重复需求；适合的案例自动重跑 | 某项判断或任务在指定条件下通过、失败或未完成；不能给整个项目加无条件的可靠认证。 |

三种状态可以在同一版本产品中并存；一项资源也可在某项能力上已验证、其他能力上仍未知。新版本发布后，旧验证保留，但不会自动转移为新版本通过。

给人的页面采用摘要、解释、对比、步骤和原文入口；给 AI 的接口保留详细材料、证据定位、关系与条件。AI 可直接读取细节，不能只有从人类摘要再次生成的长文本。

### 7.4 更新与新鲜度

“实时”定义为持续接收来源更新并维护资料状态，按来源实际发布机制设置周期。

- 所有来源和重点档案的自动检查及更新周期统一为 1 天；以来源可采集后一个日调度周期内完成处理为目标，记录实际延迟与失败，不承诺未测量的服务水平。
- arXiv 按日检查新增及修订，目标是完成当日可获得的增量；不承诺论文提交后立刻可见。
- 同时记录来源发布时间、接口或页面首次可观察时间、采集时间及可查询时间；无法获得的字段标为未知。分别报告 FieldToFit 处理延迟与可测量的发布到查询延迟。
- 版本、文档和模型卡变化触发关联档案复查；重点档案每 1 天检查关键链接和状态。采集过期、处理积压与资料已核验不能使用同一标志。

可靠性样本覆盖重复报道、项目新版本、论文修订、同名不同对象、过期文档、来源矛盾、缺失条件、数据源失败及没有匹配候选。

### 8.2 验证方法

对同一任务，在相同模型、输入和执行环境下，对比“已有搜索与文档工具”和“增加 FieldToFit 资料”。两组保留相同的执行与验证能力，隔离上下文，避免把一组发现的答案带入另一组。研究阅读任务也先定义产物及人工判断标准。

| 指标 | 判定方式 |
| --- | --- |
| 事实正确性 | 关键方法、能力、实验、条件、版本和链接能否由来源或实测支持。 |
| 条件匹配 | 是否错误违反硬性条件；未知是否被误判为满足。 |
| 候选覆盖 | 是否遗漏事先核实的适用方案或研究；明确检索范围，不宣称全网完整。 |
| 决策合理性 | 阅读、复现、直接使用、二次开发或自行实现的选择是否有依据。 |
| 实际任务结果 | 是否完成预先定义的阅读、比较、实验或最小功能产物；失败是否由 FieldToFit 的信息错误或缺失造成。 |
| 人类理解 | 用户能否说明关键概念、工具用途、适用条件和选择依据。 |
| 持续使用 | 用户是否在另一个真实任务中再次使用；自行部署后是否形成实际用途。 |

验收要求：全部 42 项有对应检查记录；12 个场景均保留产物与结果，失败项修正或明确为未通过；关键决策事实有出处或明确标注未知，未验证内容不得宣称实测。人工案例与自动检查共同使用同一结果结构。

任务收益先与基线比较，再决定是否达到了值得用户长期使用的程度，不凭内部案例数量宣布需求已验证。浏览量、点赞、Star、分享和安装数量作为传播信号，结合任务结果及复用行为判断需求是否成立。
