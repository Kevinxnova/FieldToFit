# FieldToFit 发布与版本维护

本文件是唯一发布操作指南；[CHANGELOG](../../CHANGELOG.md)是唯一版本更新历史，中英文 README 只展示当前版本与本版摘要。不再创建逐版发布说明文件。实际验收证据独立保留在 [validation](../validation/README.md)。

## 版本号规则

沿用用户 2026-09-11 确认的 x.y.z 规则：

| 位数 | 何时更新 | 如何决定 |
| --- | --- | --- |
| z | 文案、修复、页面、内容、文档或配置等日常修改 | 每个包含实际变化的交付提交递增一次；一批工作中的多次保存不是多次发版 |
| y | 新完整模块、主要阅读或取材流程的明显变化 | 先说明范围、用户影响、兼容与迁移方案，用户确认后递增，z 归零 |
| x | 产品方向、核心架构或兼容协议的重大变化 | 先说明升级原因、影响、迁移及回滚方案，用户确认后递增，y/z 归零 |

无变化的检查不生成空提交或新版本；后补文档或修复如果另作交付提交，也必须递增 z。数据库内容发布使用自己的修订、日期和原因；导出为仓库变更并提交时仍遵守应用版本规则。

## 单一来源与同步

- `backend/__init__.py` 的 `__version__` 是应用版本来源；网站及 MCP 读取实际运行版本。
- CHANGELOG 的最新版本段落维护中文和英文 `release-summary` 摘要，两种语言均由维护者核对。
- `python scripts/maintenance/release_metadata.py --write` 同步前端 package/lock 版本、中英文 README 的版本及摘要；默认不加参数只检查，不修改。
- README 的 `section` 标记固定对应章节。同步工具不自动翻译介绍；功能或社区规则变化时需人工同步两版正文。
- `python scripts/maintenance/check_repository.py` 验证最新版本记录、摘要、双语章节、前后端版本和文档链接，不以“文件里曾出现该版本号”代替一致性检查。

## 发布记录格式

在 CHANGELOG 的 Unreleased 后新增 `vX.Y.Z` 锚点与版本标题，写明日期、主题，并提供两种语言的更新摘要。随后写对应 REQ、兼容/迁移影响、实际验证链接和已知缺口。计划不写成已交付；历史记录保留原日期和范围。

README 的版本区链接到同一条 CHANGELOG 和 GitHub 标签。GitHub Release 正文从该版本段落提取，必要的相对链接转换成该标签下的 GitHub 地址，不另维护一份仓库内 Release 文档。

## 一次发布的步骤

1. 确认本批范围与版本，更新后端版本、CHANGELOG 的双语摘要及相关正文；更新受影响的 REQ、指南、README，两版事实对应。
2. 同步元数据，运行仓库检查、相关测试和构建；新增真实验收证据。没有验证的项目不能写成通过。
3. 若更新正式站点，部署后核对 `/api/health`、MCP 实际版本及受影响页面。源码版本不等于已经部署；验收记录写实际环境与结果。涉及数据迁移按管理指南操作。
4. 检查提交清单，排除凭据、私密草稿、邮件、数据库和备份。一个交付提交对应一个版本；提交说明清楚标明版本及变化。
5. 核对 GitHub 目标仓库和最新默认分支，采用保留历史的合并或快进；禁止覆盖他人提交。默认分支更新后仓库首页才会显示新 README，单独推标签不会更新首页。
6. 对已验收提交创建 `fieldtofit-vX.Y.Z` 标签并推送；历史 `v1.0.0` 等 Metis 标签不移动、不覆盖。
7. 经本次任务授权发布时，以该标签创建 GitHub Release，设置非 Draft、非 Pre-release；需要作为当前正式版时设为 Latest。确认标签指向、默认分支、Release 状态和链接。只在创建成功后报告已发布。

若检查、部署或推送失败，记录实际结果，不以 Release 状态冒充运行验收。源码可从历史标签获取；v1.1.0 之后的回退必须保留数据库中的发布与下架数据，见[内容管理](management.md)。
