# 网站反馈的去向与处理方案

2026-09-12 · FieldToFit v1.1.0。

## 当前已经实现

1. 侧栏“分享你的真实需求”进入 `/feedback`。选择类型、填写内容并点“提交反馈”后，网页向 `/api/v1/feedback` 发送请求。
2. 后端成功写入 `knowledge_feedback` 后返回 201 和记录编号，网页才显示已记录。保存失败会显示错误，保留输入内容。
3. 记录包含类型、内容、时间及可选的关联资料；通用反馈页不收集邮箱，也不要求登录。正式部署沿用 Turso；本地隔离环境使用 SQLite，具体取决于部署配置。
4. 维护者登录 `/admin`，进入“需求反馈”，可查看反馈及处理状态，填写处理依据并标记“处理中 / 已解决 / 暂不处理”。状态和说明保存在 `knowledge_feedback_actions`。当前后台按状态、关键词分页查询，每页 30 条；说明可关联 D- / CW- 内容编号。资源推荐可人工登记为待审候选。
5. 此流程没有调用邮件发送或 GitHub 创建接口，也没有通知推送、用户处理进度查询或回信功能。网站反馈不会自动出现在 fieldtofit@163.com 或 GitHub Issues。

投稿不同于网站反馈：社区页生成 Issue / 邮件草稿，由用户到 GitHub 或邮件客户端自行发送；网站通用反馈则保存到后台。

## 建议的维护方式（运营方案）

- 每周集中查看网站后台、GitHub Issue 和邮箱；明确哪些记录需要补充资料。
- 错误与失效链接优先核对；资源推荐/项目投稿走材料审核；产品需求整理为待评估 REQ 或开发 Issue。
- 处理后在后台记录结果与出处；有实际代码/内容变化时，随新补丁版本写入更新记录。
- 需要往返沟通时使用 GitHub Issue 或邮箱。当前通用表单没有联系方式，无法主动联系匿名提交者；不要承诺逐条回复。
- 后续可增加发送到维护者邮箱的反馈摘要提醒，以及用户可选择的回执方式；这些是待确认、待开发项，目前未启用。分页已实现；持续积压跟踪仍需运营记录。

本次新增统一后台的分页、处理与候选登记；测试使用本地隔离数据，不向生产后台提交测试反馈。
