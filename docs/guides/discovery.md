## 每日采集

部署配置为每天北京时间 06:30（UTC 22:30），所有来源间隔为 1 天。它与本地 08:00 选题安排是两件事：服务器产生私密发现材料，本地助手搜索补充、核对已有内容并提出具体文案。改动部署配置后，需真实部署和执行才能证明生产定时已生效。

单次日流程最多并行检查三个来源，整体预算 180 秒；每个来源还受剩余预算和单源超时限制。按北京时间自然日领取检查任务，避免执行时间略有漂移就漏掉一天；管理员立即检查可显式重试。

采集有条数与时间上限，不能把一次执行称为搜完所有信息。模型和 GitHub 检查新页并继续旧分页；官方订阅／列表保留未完成条目与已处理签名；论文沿保存的偏移续跑。默认查看近期约一周并留出重叠窗口。未读完分页标为待续跑，失败与限流不标成功；已经取得的材料先保存，后续请求失败不丢掉它们。

材料保存原始 URL、上游日期、发现及读取时间、覆盖程度、内容哈希和修订。来源仅给日期时保留日期，不补造时分秒；未知日期不以发现时间代替。正文读取失败时保留真实摘要及缺口，已有正文保留原获取时间。模型卡或 README 缺失标为未完成；已知失败的旧模型卡不会仅因日期较早而跳过重试。仅指标变化不伪装成内容更新。网络地址安全检查仍然生效，不为让来源通过而放开内网抓取。

## 每日审阅怎么用

1. 先看今日新增、优先查看、待整理、来源异常与已有内容关联计数。默认“优先查看”覆盖未处理的跨日候选，避免只看今天而丢掉昨日重要项。
2. 切换“值得关注”“待核实”或“全部发现”，可以按时间、日期、来源、类型和状态查看。翻页覆盖所有符合筛选条件的结果。
3. 打开条目查看推荐原因、未知项、带日期的关注快照，以及已获取原文。原文是私密候选材料，不会自动进入公开 MCP。
4. 如需调整优先级，填写具体理由；重新计算不会覆盖人工决定，也可恢复自动判断。旧候选可每批重新评估 100 条。
5. “加入待整理”保留在跨日队列，并创建或关联私密草稿。它不更新 For you / For your AI。具体内容与用户对齐、整理和双端预览后，才进入既有明确发布流程。

### 排序依据

| 分组 | 判定原则 |
| --- | --- |
| 优先查看 | 已获取可核对的作者／官方完整材料，并有近期发布、模型修订、仓库变化、可尝试入口或实际关注增量等依据；低 Star 项目也能进入 |
| 值得关注 | 有原始材料但完整性、时效或优先理由不足；旧正文未重新获取时明确提示，归档项目降入此组 |
| 待核实 | 只有讨论、指标、链接，或原始出处无法确认；高累计 Star 不足以越过原文门槛 |

这是一组可解释的审阅规则，不是 AI 能力评分或全文事实核验。完整材料判断使用正文覆盖和最低长度，使用入口判断依据安装／使用说明；最终内容质量仍需阅读和核对。当前规则将约两日内至少 50 个新增 Star 作为可选关注提示，必须来自同一来源两次实际观测；累计 Star、点赞、下载等单次快照不冒充增长。没有指标写未知，不按零关注处理。

同 URL、同修订合并发现出处，不同版本保留；这不等于已实现跨链接、跨对象的同一事件语义归并。跨日提醒账本和“继续／稍后／不采用”批次决定记录属于后续 REQ，不能以本批筛选界面代替。

## 数据、部署与回退

新增四张私密表保存发现、出处、指标观测和优先级；初始化建表与来源注册幂等，已有来源管理员设置不会被重复播种覆盖。现有管理员权限和请求校验继续适用。后台私密备份包含新增表；数据库、备份与候选正文不提交 GitHub。

部署前备份，部署后核对实际版本、来源表、管理员只读状态及日流程。公开动态、持续关注和图表不因采集自动更改。回退应用时保留数据库中已经发布的内容和新增私密记录，不用旧种子覆盖，详见[内容管理指南](management.md)。完整备份恢复与连续三个真实日周期需独立验收。

## v1.8.6 服务公告与私密名称追源

本批已本地开发验证，生产仍为v1.8.5。新增十二个独立服务入口和HN热门补扫，扩展日来源配置共41条，兼容来源保留。先备份，再运行现有幂等维护升级；升级注册新增来源及四张私密名称表，不覆盖管理员已有来源启停设置。实际结果见[验收记录](../validation/2026-10-07-discovery-names-sources.md)。

公告按条目保存，客户端版本、服务型号、地域、发布日与生效日分别记录。火山公开文档接口核对DocumentCode和正文；百炼合并单元格保留原年份，停用公告从官网公开嵌入数据读取完整型号表并核对公告ID，不执行脚本。只有网址可达或标题可读不算完整采集。型号内日期、页面修改日期、检索摘要都不冒充事件发布日期或官方正文。停用表保留旧型号、替代型号和完整安排，例外日期不统一赋给所有型号。

首次回补近30天及仍有效的停用计划；安静来源保留最后一条历史版本作为参考基线。每源每次最多处理5个新条目或变化，剩余队列续跑；正文更正保持原事件ID并存历史，失败保留上次成功材料。首次历史基线不进入名称组或晨报的新事件推荐，除非用户明确选中。豆包Android、Windows及网页稳定公开日志仍有缺口。

名称读取近7天候选、已获取正文及跨日已选／热门核验项，最多500项交接，超过范围显示积压。标题识别只提供线索；本地AI读取正文、提取中文或新名称并提交准确位置。已审别名按原证据复用，名称相似不自动改公开身份。同名先按官网／仓库所属／作者互链拆分，版本分别记录，原文转载只算一组，组织关系独立表达。

北京时间自然日冻结最多10个组；反复准备和撤销不能重置当天预算，每组最多3条实际检索记录和5份材料读取（追源失败也占读取名额）。已取得追源材料回传同一指纹时不重复计数，外部取得的正文与服务端追源共用材料额度。同证据“不采用”保留、不重复推荐；新证据重新核验，旧组和未完成组轮转。

### 本地AI交接顺序

沿用06:30采集、07:30准备、08:00具体提案节奏。本版未改正在使用v1.8.5接口的自动安排；部署后才可将新增交接纳入本地准备。源码提供管理员工具 `scripts/maintenance/discovery_names.py`：

1. 先只用 `--output` 导出候选和已获取正文。本步骤只读，不提前冻结十个名称组。
2. 本地AI提取名称与版本，用 `--extractions` 提交JSON数组。每项为 `ref`、当前 `fingerprint`、`mentions`；片段包含 `name`、`field`、`start`、`end`、`quote` 和可选 `version`。位置使用当前交接文本的字符位置，原文或指纹变化必须重新读取。工具接受整批最多500项，内部按50项分批导入，全部导入完成后才冻结当天队列。
3. 导入名称后工具准备当日队列，回读当天组ID、证据指纹、原始线索和额度。先沿现有链接找原文，再检索官网、作者仓库、模型卡和发布日志。管理员 `POST /api/v1/admin/workspace/names/trace` 接受 `id`、`fingerprint`、`urls`，返回正文、获取时间、覆盖和哈希；读到正文仍需核对发布主体。
4. 用 `--reviews` 导入实际核验数组，每项包含 `id`、当前 `fingerprint`、`outcome`（recommend／investigate／not_recommended）、`reason`、`searches`、`materials`、`identities` 和 `ai_relevance`。材料需完整 `body`、`quote`、`coverage=full_text`、SHA-256 `content_hash` 和原始 `url`。身份划分包含 `key`、线索 `refs`、具体 `basis`、材料URL `evidence`，可附 `author`、`organization`、`version`、`change`；推荐必须覆盖全部线索、确认AI相关性并说明变化。转载可用身份内 `families` 映射回原文。
5. 后台“新名称线索组”显示线索、身份、出处、变化和核验历史，可写理由撤销结论。核验只保存私密记录；08:00提案仍需具体选题和采用／继续核验理由。新网站草稿、公开别名／归并、发布继续逐项与用户对齐。

工具输出仅供私密交接，保存为0600；默认读取本地管理员配置并连接正式域名，可用 `--base` 指向隔离环境。凭据、候选正文、核验输出和备份不提交仓库。未部署的新接口不能以旧生产版运行成功来验收；连续三个真实自然日及实际准时交付需后续独立记录。
